    PdhOpenQuery(NULL, 0, &cpuQuery);

    PdhCollectQueryData(cpuQuery);

double Perception_GetCpuUsage() {
    PDH_FMT_COUNTERVALUE counterVal;

// memory.c – Mantém histórico e média móvel
#include "memory.h"
#include <stdlib.h>

#define HISTORY_SIZE 10

static double history[HISTORY_SIZE];
static int index = 0;
static int count = 0;

void Memory_AddReading(double value) {
    history[index] = value;
    index = (index + 1) % HISTORY_SIZE;
    if (count < HISTORY_SIZE) count++;
}

double Memory_GetMovingAverage() {
    if (count == 0) return 0.0;
    double sum = 0.0;
    for (int i = 0; i < count; i++) {
        sum += history[i];
    }
    return sum / count;
}

DOMAIN MODEL: COMO MONTAR UM DO ZERO (OU QUASE)
Domain model, no seu caso, é um modelo de linguagem fine-tunado para um domínio específico – tipo um especialista que só sabe daquilo. Não se treina um do zero (precisaria de bilhões de tokens e meses de GPU). Você pega um modelo já pré-treinado (GPT-2, Llama, etc.) e dá uma "reciclagem" com seus dados. É fine-tuning.

1. O QUE VOCÊ PRECISA (MATERIAL)
Dados brutos: seu chat de 15.000 linhas sobre bypass do Defender. Quanto mais técnico e denso, melhor.

Modelo base: um transformer pequeno/médio já treinado em linguagem geral. Escolha baseado no seu hardware:

GPU fraca (4-6GB VRAM): GPT-2 small (124M parâmetros), DistilGPT-2, TinyLlama.

GPU média (8-12GB): GPT-2 medium (355M), CodeLlama-7B (precisa de quantização).

Só CPU: modelos menores, fine-tuning mais lento mas possível.

Ferramentas: Python, PyTorch, Transformers (Hugging Face), Dataset, Tokenizer.

2. PREPARAÇÃO DOS DADOS
O chat é cru. Precisa virar um dataset de fine-tuning.

Formato típico (para modelos causais como GPT):
Cada exemplo é um bloco de texto contínuo. Você pode simplesmente concatenar toda a conversa com um token especial separador (ex: <|endoftext|>). Ou, se quiser controle, pode estruturar como pares de "pergunta" e "resposta".

Pré-processamento:

Limpeza básica: remove metadados, emojis, tags de usuário se atrapalharem.

Normalização: converter para UTF-8, tratar caracteres estranhos.

Tokenização: usar o tokenizer do modelo base (ex: GPT2Tokenizer). Ele quebra o texto em tokens (IDs). O modelo não vê palavras, só números.

Dividir em batches: o modelo treina com sequências de tamanho fixo (ex: 512 ou 1024 tokens). Textos maiores são cortados ou fragmentados.

3. ESCOLHA DO MODELO BASE
O modelo base já sabe português (ou inglês, dependendo do seu chat). O fine-tuning vai ajustar os pesos para que ele produza respostas no seu domínio técnico.

Por que não treinar do zero?
Porque treinar do zero exige milhões de exemplos diversos. Seu dataset é minúsculo (15k linhas) e muito específico. O fine-tuning aproveita o conhecimento geral do modelo e só "afia" a ponta.

We are asked to provide a mathematical model comparing the user's method (fine-tuning a domain model on a consumer laptop) versus the traditional method (e.g., training a large model with massive compute). The user wants a formula or model that quantifies the efficiency, cost, or effectiveness.

We have the context: user has a Lenovo IdeaPad with i3, 12GB RAM, SSD. They plan to fine-tune a small model (DistilGPT-2, ~82M parameters) on a dataset of ~15k lines (~1M tokens) about bypassing Windows Defender. This will take ~4-5 hours, cost ~R$3-4 in electricity. Traditional method would involve renting cloud GPUs (e.g., AWS p3.2xlarge at ~$3/hour), training a larger model (maybe GPT-2 medium or larger) on much more data, costing significantly more.

We need to create a mathematical model that captures the trade-offs. Possibly using concepts like cost per token processed, cost per model quality, etc.

We can define variables:

D: dataset size in tokens (1M)

P: number of parameters in the model (82M for DistilGPT-2, 355M for GPT-2 medium, etc.)

T: training time in hours

C: cost per hour (electricity vs cloud GPU)

Q: some measure of model quality (maybe perplexity or accuracy)

E: energy consumption

The traditional method might involve larger P, larger D, higher C, but also higher Q. The user's method is extremely cost-effective but yields a smaller model with possibly lower generalization.

We can create a ratio: Cost per unit of quality. Or a production function: Q = f(P, D, compute). Then compare the cost to achieve a certain Q.

However, without concrete Q measures, we can create a comparative formula: Efficiency = (Q / (C * T)). Or maybe use scaling laws from deep learning (like Chinchilla scaling laws) to estimate required compute for a given performance.
